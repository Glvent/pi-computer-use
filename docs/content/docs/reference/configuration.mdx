Configuration controls browser access, blocked apps, strict accessibility execution, background-only delivery, the macOS agent cursor, the macOS activity glow, and the macOS picture-in-picture view.

## Files

Global config:

```text
~/.pi/agent/extensions/pi-computer-use.json
```

Project config:

```text
.pi/computer-use.json
```

Project config overrides global config. Environment variables override both.

Example:

```json
{
  "browser_use": true,
  "managed_browser": "chrome",
  "headless": false,
  "background_only": false,
  "cursor_overlay": true,
  "activity_glow": true,
  "pip_view": false
}
```

Run `/computer-use` in Pi to show the active config and its source.

## Options

### `browser_use`

Default: `true`

When `false`, the extension refuses known browser windows. This is useful for projects that should not control browsers.

Known browser families include Safari, Chrome and Chromium-family browsers, Firefox and Firefox-family browsers such as Zen, Arc, Brave, Edge, Vivaldi, and Helium.

### `blocked_apps`

Default: password managers, credential stores, and terminals, by bundle id: Keychain Access, Passwords, 1Password, Bitwarden, Dashlane, LastPass, NordPass, Proton Pass, KeePassXC, iPhone Mirroring, Terminal, iTerm2, Warp, kitty, Alacritty, WezTerm, Ghostty, Rio, Wave, Tabby, and cmux.

Apps that the extension refuses to observe or control. Each entry is a bundle id or an app name, matched without regard to case. Input in these apps can expose credentials or run commands, and background delivery means the user may not see it happen. A blocked target fails with `app_blocked`, and `find_roots` marks its roots `blocked`. The check runs whenever a root is selected and again on every later use of it, so a config change also applies to existing states.

A configured list replaces the default list rather than extending it; copy the defaults from `DEFAULT_BLOCKED_APPS` in `src/config.ts` to keep them. `[]` unblocks everything except the system authentication agents (`com.apple.SecurityAgent`, `com.apple.LocalAuthentication.UIAgent`, `com.apple.loginwindow`), which are always blocked. A value that isn't an array of strings is reported as a config error by `/computer-use`, and that config file is ignored.

### `managed_browser`

Default: `"chrome"`

Selects `"helium"` or `"chrome"` for `launch_browser`. The debugging port is always allocated internally and isn't part of the model-facing contract.

### `headless`

Default: `false`

When `true`, actions must remain in the background. Raw pointer events, raw keyboard events, foreground focus fallback, cursor takeover, the agent cursor overlay, and the activity glow are blocked. On macOS, actions that would need synthesized pointer or keyboard input, including every `typeText` and `keypress`, fail with `foreground_required` ([macOS reference](./platforms/macos/actions.mdx#headless-policy)). When `false` (the default), Pi prefers verified semantic activation when it is credible, preserves the focus established by editable clicks for dependent keyboard input, and may retry keyboard input in the foreground when a background attempt conclusively produced no value change. Ambiguous pointer actions are never replayed blindly.

### `background_only`

Default: `false`

When `true`, actions never take over the user's pointer, keyboard focus, or frontmost window. On macOS every native action uses the `background_only` policy: AX actions and value writes run as usual, and synthesized pointer and keyboard input is always delivered to the target process with `CGEvent.postToPid(_:)`. The helper never activates or raises the target and never posts at the HID event tap, so the system cursor doesn't move. Clicks into text fields and web content are delivered as pid-targeted clicks instead of requiring the foreground. The target receives synthetic focus first, so it accepts that input while another app stays frontmost ([macOS reference](./platforms/macos/actions.mdx#synthetic-focus)). Failed background attempts are reported instead of escalating to foreground delivery. Some apps ignore pid-targeted events while they aren't frontmost; those actions report `didnt` or `foreground_required` rather than stealing focus. `headless: true` takes precedence when both are set.

### `cursor_overlay`

Default: `true`

When `true`, macOS pointer, typing, and keypress actions enqueue a click-through agent cursor animation to the native grounded point during non-headless background delivery. The cursor follows the target's display, shows a ripple when a click lands, and carries a label naming the action, such as `click`, `type`, or `cmd+a`. It stays on screen for the whole agent run and hides shortly after the run ends. Foreground actions that control the physical cursor don't display the overlay. The overlay doesn't move the system pointer, accept input, or delay the action. Set it to `false` for invisible automation. `headless: true` always suppresses it regardless of this setting ([macOS reference](./platforms/macos/actions.mdx#agent-cursor-overlay)).

### `activity_glow`

Default: `false`

When `true`, macOS displays a click-through pulsing border on every screen while a Pi agent is using one of the extension's tools. The border stays visible until the agent run ends. Each Pi session owns its indicator state, so one session cannot hide another session's active indicator. The helper removes a session's state if its connection closes unexpectedly.

The activity glow appears in user screen recordings, but never in the agent's own observations: helper captures always target a single window, so screen-edge overlays are not included. The glow is excluded from accessibility discovery. Other platforms ignore this setting, and `headless: true` always suppresses it ([macOS reference](./platforms/macos/implementation.mdx#activity-glow)).

### `pip_view`

Default: `false`

When `true`, macOS shows a small floating picture-in-picture view of the window the agent last observed while a Pi agent run is active. It shows windows behind other windows or on another Space, which background delivery leaves where they are; minimized windows can't be captured and keep their last frame. The view hides while the target app is frontmost, since its window is then already in view, and 1.5 seconds after the run ends.

The view is read-only: it never takes focus or forwards input. Drag it to move it; it keeps the chosen corner for later targets. It streams the window at up to 8 frames per second through ScreenCaptureKit, which costs some CPU while visible. On recent macOS versions, a continuous capture can make the system ask whether pi-computer-use may keep accessing the screen while bypassing the private window picker; the view needs that allowed. It's excluded from screen capture, including the agent's own observations, and from accessibility discovery. Other platforms ignore this setting, and `headless: true` always suppresses it ([macOS reference](./platforms/macos/implementation.mdx#picture-in-picture-view)).

## Environment variables

```bash
PI_COMPUTER_USE_BROWSER_USE=0
PI_COMPUTER_USE_BROWSER_USE=1
PI_COMPUTER_USE_MANAGED_BROWSER=helium
PI_COMPUTER_USE_MANAGED_BROWSER=chrome
PI_COMPUTER_USE_CHROME_EXECUTABLE=/absolute/path/to/chrome
PI_COMPUTER_USE_HELIUM_EXECUTABLE=/absolute/path/to/helium
PI_COMPUTER_USE_HEADLESS=0
PI_COMPUTER_USE_HEADLESS=1
PI_COMPUTER_USE_BACKGROUND_ONLY=0
PI_COMPUTER_USE_BACKGROUND_ONLY=1
PI_COMPUTER_USE_CURSOR_OVERLAY=0
PI_COMPUTER_USE_CURSOR_OVERLAY=1
PI_COMPUTER_USE_ACTIVITY_GLOW=0
PI_COMPUTER_USE_ACTIVITY_GLOW=1
PI_COMPUTER_USE_PIP_VIEW=0
PI_COMPUTER_USE_PIP_VIEW=1
PI_COMPUTER_USE_DELIVERY_POLICY=default
PI_COMPUTER_USE_DELIVERY_POLICY=foreground
PI_COMPUTER_USE_CDP_PORT=9222
```

`PI_COMPUTER_USE_HEADLESS=1` prohibits foreground fallback. `PI_COMPUTER_USE_DELIVERY_POLICY` is a debugging input; normal policy belongs in configuration rather than individual model calls.

`launch_browser` searches common platform install locations and `PATH`. Use `PI_COMPUTER_USE_CHROME_EXECUTABLE` or `PI_COMPUTER_USE_HELIUM_EXECUTABLE` for an AppImage, portable install, or any non-standard location. An explicit override is authoritative and must name an executable file.

## CDP browser support

`PI_COMPUTER_USE_CDP_PORT` enables Chrome DevTools Protocol support for Chromium-family browsers. Launch the browser with `--remote-debugging-port=<port>` and set this variable to the same port.

Use a dedicated, non-default profile with `--user-data-dir=<directory>`. Chrome 136 and later ignore remote-debugging switches for the default data directory as a security measure. `launch_browser` already creates a temporary, separate CDP profile and binds discovery to a randomly allocated loopback port.

When CDP is active, discovered pages participate in the same root and state system as desktop UI. `launch_browser` configures CDP automatically and returns an observed page state. `navigate_browser` and `evaluate_browser` accept only CDP browser-page states; native browser windows continue to use the normal desktop observe/act tools.

With the variable unset, CDP is inactive.
